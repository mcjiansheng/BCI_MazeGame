# LK-Mini-EEG16 间歇性断流诊断

日期：2026-09-05。本机：`D:\xht\BCI-Maze game`。

## 当前结论

用户随后确认采集盒指示灯曾全部熄灭，并已重新开机，开机后蓝灯慢闪。因此最后一段完全失联已有直接解释：采集盒处于熄灭/未工作状态，USB 接收器仍独立在线。尚未测得电量，也未确认熄灭原因，不能把低电量当成已证实结论；供电、电池与意外关机应优先排查。

设备能传输十六通道数据，且正式 Python 入口曾完成连续 60 秒采集；连接故障仍会复现。异常发生在设备控制/数据通信层，不能仅通过修改 MI 预处理、模型或图形界面解决。目前尚不能精确区分设备网络固件、USB 接收器/无线链路、SR9900 驱动或电脑 TCP 路径中的哪一项是根因。

电极信号质量是另一个问题：完整佩戴后仍有部分通道出现高幅值波动。接触不良会影响 EEG，但不能解释 `/board` 的 TCP 建连超时。没有进行带标签 MI 采集或训练真人模型。

## 厂商接入说明与本机状态

- 依据 `LK-Mini-EEG16/LK-Mini-EEG16 使用说明书 20260716.pdf` 第 7 页，配套 USB 路由器采用 STA 方式；设备自动加入 `LK-USB-Mini-EEG16`，设备固定 IP 为 `192.168.4.1`。
- 本机接口为 `以太网 7`，地址 `192.168.4.2`，网关 `192.168.4.254`。内置无线网卡仍在校园网，不代表设备接入方式错误。
- 网卡为 `Corechip SR9900 USB2.0 to Fast Ethernet Adapter`，链路 100 Mbps。驱动为 `SR9900.sys`，版本 `2.0.5.0`，日期 `2019-10-14`，NDIS 5.0。驱动较旧本身不是故障证据；未擅自替换驱动。
- 断流期间设备 ping 8/8 成功，2–6 ms；接收器网关 ping 8/8 成功，低于 1 ms。这只证明短时 ICMP 可达，不证明 TCP 采集稳定。
- 原始 TCP 端口由电脑监听，设备主动连接电脑的 `12345`；控制接口是设备 HTTP 80 端口。不能用连接设备 `192.168.4.1:12345` 的成败判断此协议。

早期短测提示接收缓冲区相关性，但默认缓冲区的长测同样失败，因此不能宣称调整 SO_RCVBUF 已找到根因或可以修复。未增加未经验证的转发代理，也未修改 Windows 全局 TCP 参数。

用户确认上述恢复期间没有改变位置、USB 插口、电源或开关状态。16:42:52 再次启动 20 秒可视化检查，在 `prepare_session()` 阶段就出现 `BOARD_WRITE_ERROR:4`，尚未创建波形窗口，未生成该次 NPZ。随后用标准库、显式禁用代理访问 `/board`，同样在 TCP 建连阶段超时。这排除了将该次失败解释为绘图耗时或 MI 模型错误的可能。

### 16:46–16:49 的进一步定位

`final_transport_probe/transport.json` 记录 `/board` 和停止请求均超时，且系统选择的源地址变成校园网 `10.4.49.180`。随后的普通/沙箱外 UDP 选路检查结果一致，`Find-NetRoute` 也选择校园网默认路由。与此同时，USB 网卡仍为 Up/Connected，`192.168.4.2/24` 为 Preferred、SkipAsSource=False，设备子网路由仍存在，因此不能简单解释为用户拔掉 USB 网卡。

为避免把选路变化误判成唯一原因，又强制从 `192.168.4.2` 发起 HTTP 与 ping：设备 HTTP 仍超时，设备 ping 0/4；同一源地址 ping 接收器 `192.168.4.254` 为 4/4、低于 1 ms。设备的 ARP 条目一度未显示，后续邻居表中以 Probe 状态出现。这将当时故障进一步指向采集盒至接收器的可达性/转发路径；源地址变化可能是失联过程的表现，单纯强制绑定源地址并未恢复设备访问。

此时接收器可达而采集盒不可达，应优先核对采集盒供电、Wi-Fi 指示状态以及采集盒与接收器的无线链路。仍需实物状态或替换对照，才能在设备电源、固件、无线连接、接收器转发问题之间定责。上述无数据探测没有启动新的采集流。

用户随后反馈“刚才黑了，我已经重新打开，现在蓝灯慢闪”。手册第 3 页定义：STA 蓝灯快闪为未连 AP、慢闪为已连 AP 未连软件、常亮为已连软件。重新开机后，16:50:02 正式入口重新选择了 `192.168.4.2`，HTTP 与通道配置恢复响应。这支持最后一次失联与采集盒熄灭相关，但不证明前面设备仍可 ping 时的 TCP 停顿也全由低电量造成。

重新开机后的 30 秒可视化检查成功建连，但先出现 Winsock 10060 接收超时，随后触发 `LK-Mini package discontinuity` 并中断，未通过验收。该次修复前的检查入口在异常时未保存 NPZ，因此没有生成 `after_power_on_30s.npz`，不能把命令指定的输出名当成已有结果。此问题随后已修复并由故障注入测试验证；未继续对佩戴中的用户反复采集。

手册第 3 页标称电池 600 mAh、连续采集超过 3.5 小时、充电约 3 小时。建议结束佩戴后按厂商说明充满电，保持位置/接收器/电脑不变，再做重复启动和持续采集对照；若满电仍自行熄灭，应交厂商检查电池、供电与固件。

## 软件修正

核对 BrainFlow **5.22.2** 的 `cyton_daisy_wifi.cpp` 与 `openbci_wifi_shield_board.cpp` 后，确认库使用 `gain_tracker` 按配置增益换算微伏。删除此前 Python 端重复的 `24/gain` 缩放；增加 x6 回归覆盖，x6/x12/x24 均直接保留库返回值。旧 x6 检查幅值偏大四倍，不能沿用其质量结论；本次 x24 记录不受该错误影响。

原始通信诊断脚本现在记录失败阶段、失败的 HTTP 请求、最长无数据间隔、帧序号和整段吞吐。只有持续收数、序号正确、速率合格且停止请求成功时才返回 0；短暂收到数据后断流返回 2。表中旧 JSON 产生于这些判据加入之前，应按逐秒字节与序号判断，不能把旧进程退出码 0 当作持续采集通过。

检查入口现在也会在连接/读数异常时给出错误原因；若已获得合法数据则保存断点前片段，标注 `capture_interrupted=true` 与 `capture_error`，并以失败码退出。不会保存或继续使用触发包序号异常的那一块数据；初始化失败时不生成虚假的空记录。波形窗口在退出时关闭。

独立 `.venv-mi` 环境的 LK-Mini 测试：51 项通过，包含连接失败与中途断流的保存/失败判定测试。Matplotlib 依赖有 14 条弃用警告，无测试失败。诊断脚本编译检查通过。
